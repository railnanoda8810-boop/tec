01 / START

そもそも「開発」って何？

コードを書く前に「何を実現したいのか」を決めること。難しい数学や大量の文法を覚えてからでなくて大丈夫。

① 困りごと何を便利にする？
→
② プログラム命令を並べる
→
③ 動作確認期待どおり？
→
④ 改善直して使える形へ
最初に覚える区別

コードを書くことは開発の一部分。開発全体には「何を作るか考える・試す・バグを直す・使えるようにする」が含まれる。AIがコードを書いても、何を成功と呼ぶかは決める必要がある。

A

プログラムとは？

コンピューターへの命令を書いたもの。print("こんにちは") は「画面にこんにちはと表示して」という命令。

B

ワークフローとは？

仕事を進める順番や仕組み。例えば「調べる→作る→試す→直す」。コードの文法とは別の話。

C

マインドセットとは？

物事を判断するときの考え方。「最初から完璧を狙うより、試して学ぶ」といった方針。

D

テストとは？

プログラムが期待どおりに動くか確かめること。「動いた気がする」ではなく、結果を見る。

知っているPythonからつなげよう

python / まずは5行例：出来具合で表示を変える
score = 6
if score >= 8:
    print("完成！")
elif score >= 5:
    print("あと少し改善")
else:
    print("まずは原因を調べよう")
このコードの意味
1
score = 6

score という名前の箱に数字の6を入れる（変数）。

2–3
if：もし点数が8以上なら

画面に「完成！」と表示する。

4–5
elif：そうではなく、5以上なら

今回は6なので「あと少し改善」と表示する。

6–7
else：それ以外なら

今回は通らない。インデント（行頭の空白）は所属を表す。

TRY IT / 理解の実験

点数を変えると何が表示される？

実際のPython実行ではなく、上のコードの条件をブラウザーで再現した練習です。

score = 6あと少し改善

if の条件は偽、elif の条件は真 → elif が動く。

index（インデックス）は「何番目か」

Pythonのリストは、通常 0番から数える。開発手法のイテレーティブとは別の言葉なので、混同しなくていい。

python / リストの基礎
features = ["録音", "保存", "検索"]
print(features[0])  # 録音
print(features[1])  # 保存
features.append("要約")
print(features)     # 4つの機能になる
考えてみよう：features[2] は何を表示する？
答えを表示

検索。先頭の「録音」が0番、次の「保存」が1番、その次の「検索」が2番。

02 / CORE

まず、この4つだけ覚える

40種類以上の名前を暗記する必要はない。基本は「直す」「増やす」「方針を変える」「順序を固める」。

01↻
Iterative

イテレーティブ

同じものを何回も直して良くする

髪の揺れ V1 → V2 → V3

作る → 見る → 直す。新しい機能は増やさなくてもいい。

注意：完成基準を先に決めないと終わらない

02＋
Incremental

インクリメンタル

使えるものを1つずつ増やす

録音 → 録音＋保存 → 録音＋保存＋検索

バージョンが上がるたび、新たに使えることが増える。

注意：部品同士を接続できる設計が必要

03≈
Agile

アジャイル

試した結果を見て計画を見直す

思っていた順番 ≠ 実際に必要な順番

方法ではなく価値観。変化へ対応し、動く成果物で学ぶ。

注意：「計画しなくていい」わけではない

04↓
Waterfall

ウォーターフォール

工程ごとに決めてから順番に進める

要件 → 設計 → 実装 → テスト

条件が固定された仕事では、最初に決めるメリットが大きい。

注意：後から大変更すると手戻りが増えやすい

誤解しやすいこと

アジャイルとウォーターフォールは完全な敵同士ではない。アプリ全体の安全設計は先に決め、画面の使いやすさは繰り返し改善する、といった組み合わせもできる。

図で比べる：直す vs 増やす

ITERATIVE / 同じものの質を上げる

1回目
試作
2回目
改善
3回目
さらに改善

※長さは概念図。品質が毎回必ず上がるという保証ではない。

INCREMENTAL / 動く機能を足していく

V1
録音
V2
録音
保存
V3
録音
保存
検索

では、両方を組み合わせると？

最初に「録音だけ」の動くアプリを作る。次に録音の失敗を修正してから「保存」を追加。その後、保存の品質を改善して「検索」を追加する。これが イテレーティブ＆インクリメンタル な進め方。

牛尾剛さんの実践との関係

本人は2026年10月の記事で、ラフな形から作り、動くサンプルを試しながら理解する反復的・増分的なスタイルを説明している。ただし「AIのコードを一切読まなくてよい」「設計は不要」という主張ではない。理解する対象を、外部仕様・構造・重要な変更へ広げている点が重要。

03 / PRACTICE

「小さく作って直す」を体験

これは本物の録音処理ではなく、アプリをどう成長させるかを学ぶシミュレーション。

MINI LAB / WORKLENS EXAMPLE

開発の段階を切り替えてみよう

V1：録音ができる

最初は録音だけを動かす。まだ文字起こしや検索は作らない。

Incremental の出発点

見分けるコツ：機能が増えたらIncremental、同じ機能を良くしたらIterative。

実際にAIへ依頼するとき

よくない指示

「完璧な録音アプリ作って」

何が完璧？ どのOS？ 保存形式は？ いつ完成？ AIが勝手に決めることが増える。

改善した指示

「まず30秒録音して保存」

Windowsで30秒録音し、WAVファイルが保存される最小機能を作り、ファイルが再生できるか検証して。

どの手法を使えばいい？

正解は「仕事による」。迷ったら、自分がいま困っていることから選ぶ。これは最初の候補を出す簡易ガイドで、唯一の正解を決める診断ではない。

今の問題主に使う手法最初の一手
何が作れるか不明PoC / Spike小さな技術実験をする
動くが品質が低いIterative / テスト同じ条件で比較する
機能が足りないIncremental / Vertical Slice1つの機能を完成させる
タスクが増えすぎKanban / 制約理論進行中を減らす
同じバグが再発回帰テスト / TDD / なぜなぜ再現条件とテストを残す

06 / VERIFY

「動いた」と「正しい」は違う

AIが「成功しました」と言っても、実際に正しいかは別。プログラムが小さな約束を守っているか、先に確認できるようにしよう。

python / 関数とテスト初心者用
def add(a, b):
    return a + b

result = add(2, 3)
print(result)         # 5 と表示

assert add(2, 3) == 5  # 成功なら何も起きない
assert add(2, 3) == 6  # 失敗：AssertionError
01

def

まとまった処理に名前をつける。add は「足し算する処理」の名前。

02

return

計算した結果を呼び出し元に返す。print（表示する）とは別。

03

assert

「この条件が成り立つはず」という確認。違うとエラーが起きる。

テストは階層で考える

単体テスト関数が正しい？
結合テスト部品同士がつながる？
E2Eテスト利用者の操作が最後まで通る？

どれか一つだけで十分とは限らない。AutoRigでは「計算が正しい」と「動画が自然」は別々に確認する。

TDDはテストを書く順番の考え方

RED：先に失敗するテストを書く → GREEN：最小コードで通す → REFACTOR：動作を変えず整理する。なお、映像の美しさ・服の自然さは自動テストだけでは判断しきれない。

08 / WITH AI

AIに任せる時の基本ルール

初心者でも、AIを使って開発することはできる。ただし「AIが仕事をした」と「目的が達成された」を分けて考える。

1つの仕事 = 目標 → 実装 → 実物で検証 → 改善

大事なのは「AIが何時間動いたか」ではなく、「使える結果が何か」。安全な調査・テストは自動化し、取り返しのつかない変更や重要な品質判断は明示的に確認する。

1

目標を明確に

「アプリを完成」より「ボタンを押すとTXTが保存される」。

2

できた証拠を要求

ログ・テスト結果・動画・実際のファイルなど。

3

次のAIへ引き継ぐ

進捗、残作業、動かし方、失敗条件を短く残す。

そのまま使える4つの指示文

① 開発を小さく始める
あなたは開発の先生兼エンジニアです。私はPythonのprintやelifを少し知っている初心者です。

【作りたいもの】（例：録音した音声をTXTに保存する機能）

最初に、専門用語を一言で説明してから作業してください。
1. 現状のコード・関連ファイルを読んで、分かっていることと不明なことを分ける。
2. まずは一番小さい「実際に動くもの」を決める。
3. 実装前に「成功したら何が見えるか」を書く。
4. 必要なコードだけ変更して動かす。
5. 実際の結果・テストログ・生成ファイルで成功を示す。
6. 失敗したら原因候補を整理して1つずつ検証する。
7. 最後に「何が変わったか」「どんな仕組みか」を、コード初心者向けに3段階で説明する。

重要：AIが「完成」と言うだけでは完成扱いにしない。
② AutoRigの破綻を調べる
対象：AutoRigの1つの破綻（例：髪のF429〜437）
目標：指定区間で見た目の破綻がなく、他区間の品質も悪化しない。

進め方：
1. 現状の再現手順・シーン・比較用動画を固定する。
2. 原因候補を別々に挙げる。推測と確認済み事実を分ける。
3. 1回の実験で原則1要因だけ変える。
4. 同じフレームとカメラで変更前後の結果を比較する。
5. 数値テストに加え、動画を見て品質判断する。
6. 改善しなければ戻す。改善したら次の区間へ広げる。
7. 成功条件・失敗条件・未検証範囲を記録する。

人間への承認要求は、危険な操作・外部公開・最終美術判断など必要な場合に絞る。
③ 初心者向けにコードを教えてもらう
あなたは初心者向けのコード解説者です。
次のコードを説明してください。

1. 1行目は何をしている？
2. 変数（名前のついた箱）の中身は何？
3. if / elif / else はどの条件で動く？
4. index はどの位置？0から数えることに注意。
5. printで何が表示されるか、実行前に予想させて。
6. 予想と結果が違ったら理由を教えて。
7. 最後に数字や条件を1つ変えた練習問題を1問出して。

専門用語は必ず初出で説明し、AIの回答を読んで終わりにせず、私の説明を待ってください。
④ AIに安全な実装ルールを作らせる
このプロジェクトで次の作業をする前に、あなた（AI）が守るルールを短く整理してください。

- 最終的にほしい「動く成果物」
- 現状のどのファイルが関係するか
- 何をもって成功とするか（受入条件）
- 変更してはいけない範囲
- 最小実装と最小テスト
- 失敗したら何を戻すか
- 他のAIへ引き継ぐための短い進捗記録

報告書の作成数やAIの作業回数より、利用できる成果物の完成を優先する。
一度に多くのAIを動かせば速い？

独立した調査は並列でよいが、同じファイルを別々に編集すると統合時に衝突する。複数AIを使うなら、担当範囲・成果物・統合責任・検証方法を決める。
